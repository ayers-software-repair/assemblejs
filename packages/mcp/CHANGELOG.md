## 1.0.0-next.1

### Patch Changes

## 1.0.0-next.0

### Major Changes

- The first prerelease on the next channel: the server, the command line and create, the agent surface, the devtools, the renderers for React, Preact, Vue, Svelte, Solid and Lit, and the template renderer for EJS, Handlebars, Markdown, Nunjucks and Pug.

### Minor Changes

- The server finds its project's root from how it was started: the directory given as its one argument, else the one Claude Code names in `CLAUDE_PROJECT_DIR`, else where it was started. A root that is no directory is refused at start, on standard error, with exit code 2.
  
  `create_project` writes the agent instructions and registrations a new project carries, and scaffolds into a root that already holds some of them, the registration that started the server for one: its own part of each file is brought up to date and everything else in it is kept.
  
  `RULES`, `findRule` and `Rule` are no longer exported from here; they are `@asmjs/cli`'s, which this package depends on and explains.
- The agent surface lists four prompts, which a client shows its user as commands: `add_assembly`, `place_assembly`, `make_page` and `fix_findings`. Each answers a brief, one message in the person's voice, that gives the agent the order to work in, where to stop and ask, and what each tool's answer means. A prompt takes a name of the framework's own shape, or one of its renderers, and refuses anything else as invalid.
  
  `pageDocument(title, placed)` is exported from the command line: the whole document a new project's page is written with, which the prompt for a page hands over. The instructions a new project is written with say which views `render_assembly` and `compose_page` show at once and where the rest are seen.
- A view places a child by writing the directive, and is never handed one. `children` is gone from `MarkupInput`, `RenderInput`, every renderer's `AssemblyProps` and the template engines' locals: a view renders once, and the server puts each child where its directive stood.
  
  A framework view writes the directive with its renderer's slot, by name and an optional view: `<Slot name="cart" />` in React, Preact, Vue and Solid, `{@html slot("cart")}` in Svelte, `${slot("cart")}` in Lit, each imported from the renderer's `/client` entry. A slot writes the same markup on the server and in the browser, so a parent hydrates around the child the server placed and leaves it alone when it renders again. A template view writes `<assembly name="cart"></assembly>` in its own markup, as a page does; Pug writes it as `assembly(name="cart")`. `placementDirective(name, view?)` in `@asmjs/core/client` is the one definition of that markup, and refuses a name or a view that is not a segment.
  
  A Lit view holds a Lit assembly only behind a shadow root, which `export const shadow = true` in that assembly's view gives it. Lit hydrates a view by reading every marker in its tree, so a Lit assembly left in the same tree is refused by name when the view mounts.
  
  The agent rule `children-arrive-as-strings` is replaced by `a-view-places-a-child-with-the-directive`.
- `assemblejs://project` answers a project's whole shape: every page with its route, what it places and the policy it declares; every assembly with its files, what its view places and where it is placed; every api's route; and what the config declares. `assemblejs://assembly/<name>` answers one assembly with every placement of it, and each assembly is listed as a resource of its own. All of it is read from the sources and nothing is run: a value a source computes reads `(computed)`, and what a file that cannot be read would have said reads `(unread)`. The command line exports the reader, `readShape`. An assembly in the project's answer has `client` and `browserHalf` where it had `hasClient`.
- What a view places is known before it renders. `AssemblyView.placements` holds what a view's source is known to place, each a name and, where the source writes one, a view. The build reads it from every view and writes it into the registry: the directives of a plain html, EJS, Handlebars or Nunjucks view, and the slots of a React, Preact, Vue, Solid, Svelte or Lit one. A Pug view is read only when it renders.
  
  Boot holds those placements as it holds a page's: a name with no assembly, a view the assembly lacks and a view that leads back to itself are refused before anything listens. A page carries the runtime when an assembly it places, or one beneath it, has a browser half, so a deferral or a stream on a page whose only placement is a plain html parent is no longer refused. A deferred placement is served with the browser files of everything its view is known to place, linked ahead of the answer that brings them.
  
  `check` reports the same, in the file that places it, and three things only it can know: a placement whose name is computed (`a-placement-is-named-where-it-is-written`), an assembly placed inside itself (`an-assembly-is-never-its-own-ancestor`), and a Lit assembly in a Lit view's own tree with no shadow root between them (`lit-holds-lit-behind-a-shadow-root`).
  
  The agent surface renders and composes through the server's own transport: `render_assembly` and `compose_page` show every assembly a view places composed inside it, with the account of each beneath its parent, and say why one fell back. `place_assembly` takes `in`, an assembly whose view receives the placement, in place of a page; a view its author writes as source is not edited, and the answer is the line to write.
- `compose_page` takes a page by its name and composes its template under the policy its declaration writes, as the server plans it; a placement from another server is composed deferred, so nothing is fetched. The prompts and the instructions `new` writes say so.
- The agent surface answers `assemblejs://contract`: the three endpoints, their headers with their shapes, the manifest's fields and the envelope, every name the one the server writes, for an agent implementing an assembly on another server. The instructions `new` writes name it.
- `render_assembly` answers the data the assembly's services returned when the project's dev server rendered it, read from the island of the envelope the server answered; it answered an empty object on every path.
- `dev` records the url its server listens on under the project's root, `.assemblejs/dev.json`, for as long as that server runs. The agent surface's `render_assembly` and `compose_page` find it, ask its health, and then ask that server's content endpoint for every assembly and placement, so a framework or template view is shown as the project serves it, services and all, and nothing of the project's code runs in the tool. Without a dev server running, a plain html view is rendered as before and any other is refused with the word to start it. The command line's `Io` gains `remove`.
- While the project's dev server runs, `render_assembly` and `compose_page` say what failed on it: an assembly that failed there is answered with the id the dev server logged its failure against, and each placement that fell back inside an answer that stands is named with its own id, where before the first carried an id in nobody's log and the second said nothing.

### Patch Changes

- Updated dependencies
  - @asmjs/core@1.0.0-next.0
  - @asmjs/cli@1.0.0-next.0
- What a project's author is told now holds in a project. An assembly made from a directory has one view, `default`, so the rule `a-placement-is-named-where-it-is-written` and the fix `check` gives no longer say a view may be computed, which in a project names a view the child does not have. The directive is written closed, `<assembly name="..."></assembly>`, wherever a rule, a finding or a tool's description shows it: an opening tag alone is refused where it is read. What `check` accepts and refuses of a placement is unchanged. The instructions a project is written with carry the two rules' new words, so `check` asks a project written before this to run `assemblejs add agents`.
- `check` and the agent surface read nothing outside a project's root. Every file a reader opens is held to the root after each link is followed to where it really leads: a link under the root that leads out of it, a directory that is one, and a view's import that climbs out are not opened, not listed and not followed. Each is a finding by a new rule, `a-project-stays-inside-its-root`, and what it would have said reads `(unread)` in `assemblejs://project`. Before this, a finding could quote what such a file held. `add agents` writes nothing through a link that leads out, and a stylesheet's `url()` written outside its assembly is refused without being looked for. Discovery takes the project's root (`discoverAssemblies(root)`, `discoverPages(root)`, `discoverApis(root)`), the readers that open a file take it too, and `insideRoot`, `readInside`, `leadsOut`, `followLinks` and `OutsideRootError` are the command line's, which the agent surface takes them from.
- Each published entry point names its own specifier in a `@module` comment, which is the name the API reference lists it under. Nothing any of them exports changes.
- The command and the library of each package are built to share one copy of the code where each carried its own. Nothing either does changes; the command line's tarball is about two thirds the size it was.
- A page, an assembly and an api file are tested against the vocabulary's own shape of a name, core's `SEGMENT`, where each carried a copy of it. A project's name has one definition, `PROJECT_NAME`, exported from the command line and asked by `new` and by `create_project`. Nothing that was accepted or refused changes.
- A project sets how deep composition goes and how many placements one request composes in its config file: `limits: { depth, placements }` in `assemblejs.config.ts`, each a whole number, each optional, one left out keeping the default of 8 and 256. The server reads them at boot and refuses a value outside its bounds. `createServer` takes `limits` in place of `maxDepth`. `check` and the agent surface show them as they show every setting.
- The descriptions of `render_assembly` and `compose_page` say what they show: a plain html view, with no service run and so no data, and any other view answered with the reason it was not rendered. Nothing either tool does changes.
- A dev server told to listen on every interface, or on one of this machine's own addresses, is still found by the agent surface. `dev` records the address it can be asked at from this machine, the loopback of the same family where it listens on every interface, and `render_assembly` and `compose_page` believe a recorded address that is a loopback name or an address of one of this machine's interfaces. Any other host in the record is another machine's and is not asked.
- A new project's guide link and its agent instructions now name the documentation of the channel it was made from: `/next/` for a prerelease and the product's own address for a stable.
  The agent instructions open with the address of `llms.txt` and `llms-full.txt`, and every package's `homepage` is `https://assemblejs.com/`.
- What the command line and the agent surface write into a file a project already has is written as that file is laid out. A placement goes on a line of its own at the indentation of what it stands beside, in the file's own line ending, and inline only where what it stands beside shares its line; into an empty body it goes one step in, as the starter writes one. Where a template writes no body, a placement at its start goes after the doctype and the head, never before them. A tag is read by its whole name and not inside another tag's attribute, so `<body-card>` and `title="<body>"` are not the body. `place_assembly` says when the template now places that assembly more than once, and refuses a template it cannot read wherever it was asked to put the placement.
  
  `add agents` writes what it adds to an `AGENTS.md`, a `CLAUDE.md` or a registration in that file's own line ending, and reads a registration through a byte order mark and writes it back behind one, where it had refused the file as not JSON.
  
  `add assembly`, and the agent surface's `add_assembly`, say what the view's renderer needs that the project has not installed, as `check` does.
- A project can be made in a directory that is already there. `assemblejs new .`, and `npm create @asmjs .`, make it in the directory the command works in, named for that directory, where each had refused the dot as a name and suggested "assembly". `new` and the agent surface's `create_project` ask one decision of what the directory may hold: what the starter does not write is left alone, a README is kept as its author wrote it, a `.gitignore` keeps every line and gains the starter's entries it lacks in its own line ending, and the files a project carries for its agents are brought up to date. Anything else the starter would write, or anything under `src`, is named and nothing is written. `create_project` sends an agent to `add_assembly` only where the root holds a `package.json`.
  
  A name with nothing usable in it is answered with an example of the thing being named, so a project, a page or an api is no longer told to call itself "assembly".
  
  Two exports change with it. `suggestName` takes that example as a second argument, which it requires. `isOccupied` is exported by `@asmjs/cli`, the one reader of whether anything is at a path, and no longer by `@asmjs/mcp`.
  
  The agent surface answers a refusal as an answer. A tool that met a path leading out of the project, a link to nothing, or a read or a write the system refused had its error carried by the protocol as a line of text; each is now `ok: false` with its problems, the path's with its rule and its fix. A dev server's record that is a link out of the project is read as no record, where it had ended `render_assembly` and `compose_page`.
- `check` says what it used to pass over, and `add` writes only into a project. A file that is nearly a declaration and is not read (`cart.services.ts`, `service.ts`, `home.pages.ts`, `orders.apis.ts`, a `src/apis` beside `src/api`) is a finding with the name that would be read, where it was left out of the build in silence. A README, a test or a story beside a view is no longer a second view that made its assembly no assembly; a Markdown file is a view only under its assembly's name. A link under `src` that leads nowhere is a finding of `a-project-stays-inside-its-root` (`DeadLinkError`, a refusal of the root guard's), where `check`, `build`, `dev` and `deploy` each ended in the system's own error and a stack. `add assembly` writes nothing where there is no project, so a mistyped `--cwd` makes no directory, and nothing through a link that leaves the project or leads nowhere, as the agent surface's `add_assembly` already would not. A placement naming an assembly whose directory is there and broken is told to mend the directory, not to add it.
- `perf` no longer fails a project that guards a page. It asks every page as a visitor who has not signed in, and a page that answers such a visitor 401 or 403 was counted as one that did not answer, so no project with a guarded page could pass. It is now reported as not weighed, as a page whose route has a parameter is, and the command goes on. A file an open page links that answers 401 is still a failure. And `check` and the agent surface say "an ejs assembly" and "an html assembly", where they said "a".
- The agent surface asks only this machine's dev server, and waits for it only so long. The address in `.assemblejs/dev.json` was asked for whatever it was, and any server that answered its health path with a 200 was taken for the project's; it is believed only where it is plain http on a loopback name and answers the framework's own health. `render_assembly` waited on the dev server without end; it waits ten seconds and says the server did not answer. `place_assembly` wrote an assembly into one it already led to and answered done, where only an assembly placed in itself was refused; a child that leads to the parent at any depth is refused before anything is written, with the way it leads there (`leadsTo`). And a placement naming an assembly whose directory is there and broken is told to mend the directory, where it was told to add what `add_assembly` then refused as taken.
- `compose_page` and `render_assembly` take what a visitor arrives with: `params`, a value for each parameter of the page's route, and `query`. Every placement's request is given them as a page's composer gives them, so a page at `/product/:sku` is shown as one product's. Until now both rendered for nobody, with no value for any parameter, and an agent was shown a page no visitor is. `compose_page` holds the values to the route the page declares: one for a parameter the route has not is refused with the ones it has, and a parameter left out is composed without and said among the problems. The three tools that show a project and change nothing are registered by `registerSeeingTools`, exported beside `registerAuthoringTools`.
  
  `@asmjs/core` exports `routeParameters`, the one reading of the names of a route's parameters. The server's route table, `perf`, which does not weigh a page whose route has one, and the agent surface each read it, where each had told a parameter by itself.
- The build is a package of its own. `@asmjs/build` is new: what is known of a project by its directories, the modules generated for it, the bundles a project becomes and the dev loop, which were part of `@asmjs/cli`. The command line depends on it and keeps its verbs, so a project installs and runs what it did: `assemblejs build` and `assemblejs dev` are unchanged. A program that imported those names from `@asmjs/cli` imports them from `@asmjs/build`; the command line no longer exports them.
- The checks are a package of their own. `@asmjs/check` is new: the rules a project is held to, every problem found in one without building it, a project's shape, what its pages weigh, and the text of the files written for a project's agents, which were part of `@asmjs/cli`. The command line depends on it and keeps its verbs, so `assemblejs check` and `assemblejs perf` are unchanged. A program that imported those names from `@asmjs/cli` imports them from `@asmjs/check`; the command line exports its verbs and what `new` writes, and no more.
- The agent surface installs as two packages, and no longer brings the protocol SDK's dependency tree with it. The protocol SDK is bundled into `@asmjs/mcp`, `THIRD_PARTY_NOTICES.md` in the package carries its notices, and zod is a dependency.
- The instructions `new` writes and the brief for adding an assembly say what the two tools show now: any view through the project's running dev server, and a plain html one with nothing running. They told an agent a framework view is shown nowhere.
- `render_assembly` and `compose_page` send the dev server the ids a composer sends, a uuid for the page and for each placement. They sent ids of their own making, which the content endpoint refuses with a 400, so with a dev server running every assembly was refused and every placement fell back. A request the server refuses is now said with what the server said was wrong with it.
