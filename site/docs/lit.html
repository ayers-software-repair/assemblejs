For Lit developers

A Lit assembly is a view, cart.lit.ts, a function from the assembly's props to a Lit template, and the elements it places are yours. The server renders it, each element into a declarative shadow root; the browser hydrates it, and the page it sits on can hold React or Svelte beside it. Everything on this page is from the repository's own examples, its design document or its tests.

Install the renderer

npm install @assemblejs/renderer-lit lit
One renderer package per framework, so a project that has no React never installs React. Lit 3.3.3 or newer in the 3.x line; the renderer's own machinery, @lit-labs/ssr for the server and @lit-labs/ssr-client for the browser, comes with it.

The view

npx assemblejs add assembly cart --renderer lit
Writes src/assemblies/cart/cart.lit.ts and nothing else: the directory is the assembly, and the .lit infix says the framework, because a Lit view is TypeScript like a service or a client file. Your server file does not change. 
import type { AssemblyProps } from "@assemblejs/renderer-lit";
import { html } from "lit";

export default (props: AssemblyProps) => html`<p>cart ${Object.keys(props.data).length}</p>`;
Two props
data is what the assembly's services returned, as JSON; AssemblyProps takes its shape as a type argument. events is this assembly's own events object, handed in as a prop because a template function has no context to read it from; the view hands it to its elements as a property. No request, no headers, no cookies cross to the view, and nothing of the assemblies it holds: it places those with a slot. A second .lit.ts in the directory is one of the view's own elements, not a second view.
An assembly inside this one
slot() places another assembly where it stands in the view's template, by name. The server puts it there, and the page's runtime mounts it as it mounts this one. The name is written as a string. A second argument names a view, and may come from data. 
import { slot } from "@assemblejs/renderer-lit/client";
import { html } from "lit";

export default () => html`<section class="cart">${slot("price")}</section>`;
A Lit view holds a Lit assembly only behind a shadow root. Lit hydrates a view by reading every marker in its tree, and would read that assembly's as its own, so the view refuses to mount and check says so first. The assembly it holds takes one line: export const shadow = true in its view. An assembly written in anything else needs nothing.
What the server renders
The template with the markers hydration reads, and every Lit element in it rendered into a declarative shadow root, so the page is whole before any script runs. An element's static styles are left out of that root, because Lit writes them as an inline <style> and the page's default policy refuses one; the browser adopts the same styles as constructed sheets when the element hydrates, so an element is styled once it hydrates.

Data from the server

cart.service.ts
A service beside the view runs on the server before the render and returns the data. It is given the request's query and the route params of the page that placed the assembly, and the same function answers the assembly's data endpoint, so the two cannot disagree. The view reads the result as props.data. 
import { defineService } from "@assemblejs/core";

export default defineService({
  name: "label",
  schema: { properties: { label: { type: "string" } }, required: ["label"] },
  run: () => ({ label: "Clicked" }),
});

Talking to the rest of the page

.events=${props.events}
There is no useEvents for Lit: the view binds the events object to an element as a property, and the element subscribes when the property arrives, which is at hydration, after the element is defined. send stamps the sender and on returns its unsubscribe; what is still subscribed when the page unmounts its assemblies is released then. The counter from the frameworks example sends on every click and hears every other counter on the page, React, Svelte, Preact, Vue or Solid, with no adapter between them. 
import type { Events } from "@assemblejs/core/client";
import type { AssemblyProps } from "@assemblejs/renderer-lit";
import { LitElement, css, html } from "lit";

// A Lit element: rendered into a declarative shadow root on the server, hydrated in the browser.
class LitCounter extends LitElement {
  static override properties = {
    count: { state: true },
    heard: { state: true },
    events: { attribute: false },
  };
  static override styles = css`
    button {
      color: rgb(120, 0, 120);
    }
  `;
  declare count: number;
  declare heard: string;
  declare events: Events | undefined;
  private stop: (() => void) | undefined;

  constructor() {
    super();
    this.count = 0;
    this.heard = "nothing";
  }

  // The element is defined before hydration hands it the assembly's events, so it subscribes
  // whenever they arrive or change, not when it connects.
  override willUpdate(changed: Map<PropertyKey, unknown>): void {
    if (!changed.has("events")) return;
    this.stop?.();
    this.stop = this.events?.on("counted", (message) => (this.heard = message.from.name));
  }

  override disconnectedCallback(): void {
    super.disconnectedCallback();
    this.stop?.();
  }

  override render() {
    return html`<button
        type="button"
        id="lit-bump"
        @click=${() => {
          this.count += 1;
          this.events?.send("counted", { count: this.count });
        }}
      >
        lit ${this.count}
      </button>
      <span id="lit-heard">${this.heard}</span>`;
  }
}
if (customElements.get("lit-counter") === undefined)
  customElements.define("lit-counter", LitCounter);

export default (props: AssemblyProps) => html`<lit-counter .events=${props.events}></lit-counter>`;
On the server
The view renders with the server's events, as it hydrates with the page's: a subscription made there is accepted and never called, and last answers nothing. The same file runs on both sides without asking which one it is on.
events.last(topic)
A page can name one stream, and every topic the stream sends keeps its last message, because the stream opens while assemblies are still loading. An element that is handed the events late reads what it missed with last, then subscribes.

When it runs in the browser

Lit's hydration support, first
The build imports @assemblejs/renderer-lit/hydration-support first in the page's one script, before the runtime and before any assembly's own module, because Lit's support for hydrating elements a server rendered must be installed before Lit's element base loads. Nothing to do: the renderer's client entry imports it first as well, for a page assembled some other way.
export const mount = "visible"
Declared by the view, beside its default export. load mounts at once and is the default; idle waits for the browser to be idle; visible waits until the envelope scrolls into view; none never mounts: the runtime reads the mode and leaves the assembly as the server sent it, and the page still carries the runtime for the rest. A value that is none of the four reads as none, so a typo cannot start code running on a page whose author was saying when it should run.
export const shadow = true
Renders the whole assembly in a shadow root of its own, outside any element's: no page style reaches in, none of its own leaks out. The box from the shadow example is a template with no element in it, whose button counts through its own binding. 
import type { AssemblyProps } from "@assemblejs/renderer-lit";
import { html } from "lit";

export const shadow = true;

// A template whose button counts by re-rendering the view in place, through its own binding.
export default (props: AssemblyProps) => {
  void props;
  return html`<button
    type="button"
    class="bump"
    id="lit-bump"
    @click=${(event: Event) => {
      const button = event.currentTarget as HTMLButtonElement;
      const count = Number(button.dataset["count"] ?? "0") + 1;
      button.dataset["count"] = String(count);
      button.textContent = `lit ${String(count)}`;
    }}
  >
    lit 0
  </button>`;
};

Styles

static styles
An element's own styles work as they do anywhere in Lit, adopted into its shadow root when it hydrates, as above.
cart.css
A stylesheet beside the view styles the template itself, outside the elements. It is compiled with a scope derived from the assembly's name, so two assemblies written apart cannot collide; the view in its own shadow root links a second sheet, built for that root. Every file it names beside it, an image or a font, is built with it; one it cannot carry is a build problem, not a broken link found later. The box above has one rule beside it. 
.bump {
  color: rgb(0, 128, 0);
}

On a page

<assembly name="cart"></assembly>
In any page template under src/pages. A local placement needs no policy at all.
home.page.ts
Policy, when a placement needs any, lives in the page's own file: a deadline in milliseconds, markup to show when the assembly does not answer, whether its failure fails the page, or a deferral the browser fills after load. 
import { definePage } from "@assemblejs/core";

export default definePage({
  place: { cart: { deadline: 500, fallback: "<p>Cart unavailable</p>" } },
});

Run it

npm run dev
Builds, starts, and rebuilds on every change.
npx assemblejs check
Every problem found without building: a placement naming an assembly that does not exist, policy nothing reads, the renderer not installed, a .client.ts beside a view whose browser behaviour is its elements already.
npx assemblejs build
Writes dist/server.js and the browser files. Production is node dist/server.js with no bundler.
