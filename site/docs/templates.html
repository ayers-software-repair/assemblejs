For template authors

A template assembly is one file in EJS, Handlebars, Nunjucks, Pug or Markdown, rendered on the server by its own engine and nothing else; it ships no JavaScript unless a file beside it asks for some. The page it sits on can hold React or Svelte beside it. Everything on this page is from the repository's own examples, its conformance fixtures, its design document or its tests.

Install the renderer

npm install @assemblejs/renderer-templates
One package for the five languages, with no framework to install beside it: the five engines are its own dependencies, and each is imported the first time a template in its language renders, so a project using one language never loads the other four.

The view

npx assemblejs add assembly cart --renderer ejs
Writes src/assemblies/cart/cart.ejs and nothing else: the directory is the assembly, and the extension names the language, so nothing is registered and your server file does not change. --renderer handlebars writes cart.hbs, nunjucks writes cart.njk, pug writes cart.pug and markdown writes cart.md. The first four read a title from the data and fall back to the assembly's name; the Markdown one is a heading. 
<p><%= data.title ?? "cart" %></p>
<p>{{#if data.title}}{{data.title}}{{else}}cart{{/if}}</p>
<p>{{ data.title or "cart" }}</p>
p= data.title || "cart"
# cart
Two names, data and children
data is what the assembly's services returned, as JSON. children is rendered HTML by placement name, for an assembly that holds others. Nothing else reaches the template: no request, no headers, no cookies. In EJS the two are the template's only locals, in strict mode.
Escaped by default, children as they are
What a template writes from data is escaped by every engine that reads it; children is already HTML and is written as it is: by the engine's raw form in EJS and Pug, and as a safe string in Handlebars and Nunjucks, so the same brace writes it. From the renderer's tests: given a name of <b> and a child inner of <i>child</i>, each of these four renders <p>&lt;b&gt;<i>child</i></p>. 
<p><%= data.name %><%- children.inner %></p>
<p>{{data.name}}{{children.inner}}</p>
<p>{{ data.name }}{{ children.inner }}</p>
p #{data.name}!{children.inner}
Pug's escaping leaves ' as it is: write an attribute with Pug's own syntax, a(title=data.name), rather than inside a single-quoted attribute in raw HTML.
Markdown is prose
A .md view reads no data and places no children, and HTML written inside it is shown as text; an .html view is the place for markup. The notes from the templates example. 
# Five template languages

Each card below is written in its own language and rendered on the _server_. None of them
ships any JavaScript.
A view is one file
An include, an extends, an import or a partial from another file is refused, so a template never reads from wherever the server happens to run; a Handlebars inline partial, defined in the same file, renders. Handlebars templates compile in an instance of the package's own, so a helper or partial another library registers on the shared Handlebars never reaches them. An error names the view's file, which the engines' own messages do not.

Data from the server

ejs-card.service.ts
A service beside the view runs on the server before the render and returns the data. It is given the request's query and the route params of the page that placed the assembly, and the same function answers the assembly's data endpoint, so the two cannot disagree. The templates example gives each card a title with markup in it, which the template writes escaped. 
import { defineService } from "@assemblejs/core";

// A title with markup in it, which the template writes escaped.
export default defineService({
  name: "card",
  schema: {
    properties: { title: { type: "string" }, items: { type: "array", items: { type: "string" } } },
    required: ["title", "items"],
  },
  run: () => ({ title: "Written in ejs <em>escaped</em>", items: ["one", "two"] }),
});
ejs-card.ejs
The card, reading the title and looping the items. 
<section class="card" data-engine="ejs">
  <h2><%= data.title %></h2>
  <ul><% for (const item of data.items) { %><li><%= item %></li><% } %></ul>
</section>
handlebars-card.hbs
The same card in Handlebars. 
<section class="card" data-engine="handlebars">
  <h2>{{data.title}}</h2>
  <ul>{{#each data.items}}<li>{{this}}</li>{{/each}}</ul>
</section>
nunjucks-card.njk
The same card in Nunjucks. 
<section class="card" data-engine="nunjucks">
  <h2>{{ data.title }}</h2>
  <ul>{% for item in data.items %}<li>{{ item }}</li>{% endfor %}</ul>
</section>
pug-card.pug
The same card in Pug. 
section.card(data-engine="pug")
  h2= data.title
  ul
    each item in data.items
      li= item

When it runs in the browser

Nothing, unless you say so
A template view is server markup and nothing more. An assembly made of one is declared none: it never mounts and ships no JavaScript at all.
cart.client.ts
A .client.ts beside the view is the assembly's browser half. It default-exports an object whose mount is given the envelope, already resolved, the assembly's data, and a context holding its id, its name, its view and its events object, scoped to it as any framework's is, and returns a handle the runtime calls to unmount. The badge from the conformance suite, an .html view with a browser half, is the whole shape. 
// A browser half, so the assembly has a script and a stylesheet among its assets and the page
// carries the runtime that opens its stream.
export default {
  mount: (element: Element | ShadowRoot) => {
    if (element instanceof Element) element.setAttribute("data-mounted", "");
    return { unmount: () => undefined };
  },
};
When it mounts
When the page loads. The mount modes and the shadow root are a framework view's exports; a template view has none, so an assembly with a .client.ts mounts at once and in the page's own tree.

Styles

cart.css
A stylesheet beside the view is compiled with a scope derived from the assembly's name, so two assemblies written apart cannot collide. Every file it names beside it, an image or a font, is built with it; one it cannot carry is a build problem, not a broken link found later. The EJS card's sheet, beside it. 
.card {
  border: 1px solid currentColor;
  padding: 0.5rem;
}

On a page

<assembly name="cart"></assembly>
In any page template under src/pages. A local placement needs no policy at all. The templates example places one assembly per language on one page. 
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <title>five template languages, one page</title>
  </head>
  <body>
    <assembly name="notes"></assembly>
    <assembly name="ejs-card"></assembly>
    <assembly name="handlebars-card"></assembly>
    <assembly name="nunjucks-card"></assembly>
    <assembly name="pug-card"></assembly>
  </body>
</html>
home.page.ts
Policy, when a placement needs any, lives in the page's own file: a deadline in milliseconds, markup to show when the assembly does not answer, whether its failure fails the page, or a deferral the browser fills after load. 
import { definePage } from "@assemblejs/core";

export default definePage({
  place: { cart: { deadline: 500, fallback: "<p>Cart unavailable</p>" } },
});

Run it

npm run dev
Builds, starts, and rebuilds on every change.
npx assemblejs check
Every problem found without building, among them a template its engine cannot read: each view is compiled with the engines the project's own package loads, and one that throws is reported naming the file and what the engine said. Markdown never fails to compile. What an engine resolves only as it renders, a value the data has not or a helper the template lacks, throws then, and the placement falls back.
npx assemblejs build
Writes dist/server.js and the browser files. Production is node dist/server.js with no bundler.
