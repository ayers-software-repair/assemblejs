For Solid developers

A Solid assembly is a component in a file whose name says it is Solid, compiled by Solid's own compiler. The server renders it, the browser hydrates it, and the page it sits on can hold React or Vue beside it. Everything on this page is from the repository's own examples, its design document or its tests.

Install the renderer

npm install @assemblejs/renderer-solid solid-js
One renderer package per framework, so a project that has no React never installs React. Solid 1.9.15 or newer in the 1.x line. Solid's JSX is compiled by Solid's own Babel preset, a dependency of the renderer, which the build loads from the project's own copy of the renderer, so there is nothing else to install.

The view

npx assemblejs add assembly cart --renderer solid
Writes src/assemblies/cart/cart.solid.tsx and nothing else: the directory is the assembly, and the .solid infix says the framework, because React, Preact and Solid all write .tsx. Your server file does not change. The scaffold reads props.data and does not destructure. 
import type { AssemblyProps } from "@assemblejs/renderer-solid";

export default function Cart(props: AssemblyProps) {
  return <p>cart {Object.keys(props.data).length}</p>;
}
Two props, nothing else
data is what the assembly's services returned, as JSON; AssemblyProps takes its shape as a type argument. children is rendered HTML by placement name, for an assembly that holds others. No request, no headers, no cookies cross to the component. A component in the assembly's directory compiles as Solid like the view does.
What the server renders
Rendering is synchronous, because an assembly's data comes from its services. A resource is not rendered on the server: the server sends its Suspense fallback, and hydrating a fallback is not supported. A lazy component renders on the server only once its module is loaded, which a server does by preloading it. The inline script Solid writes for its own bootstrap is left out of the markup, because the page's policy refuses it; each assembly hydrates with a hydration state of its own, so two Solid islands on one page both keep the elements the server sent.

Data from the server

cart.service.ts
A service beside the view runs on the server before the render and returns the data. It is given the request's query and the route params of the page that placed the assembly, and the same function answers the assembly's data endpoint, so the two cannot disagree. The component reads the result as props.data. 
import { defineService } from "@assemblejs/core";

export default defineService({
  name: "label",
  schema: { properties: { label: { type: "string" } }, required: ["label"] },
  run: () => ({ label: "Clicked" }),
});

Talking to the rest of the page

useEvents()
From @assemblejs/renderer-solid/client. The object is scoped to this assembly: send stamps the sender and on returns its unsubscribe. Subscribe in onMount and hand the unsubscribe to onCleanup; what is still subscribed when the page unmounts its assemblies is released then. The counter from the frameworks example sends on every click and hears every other counter on the page, React, Svelte, Preact, Vue or Lit, with no adapter between them. 
import { useEvents } from "@assemblejs/renderer-solid/client";
import { createSignal, onCleanup, onMount } from "solid-js";

export default function SolidCounter() {
  const events = useEvents();
  const [count, setCount] = createSignal(0);
  const [heard, setHeard] = createSignal("nothing");
  onMount(() => {
    const stop = events.on("counted", (message) => setHeard(message.from.name));
    onCleanup(stop);
  });
  return (
    <section>
      <button
        type="button"
        id="solid-bump"
        onClick={() => {
          setCount(count() + 1);
          events.send("counted", { count: count() });
        }}
      >
        solid {count()}
      </button>
      <span id="solid-heard">{heard()}</span>
    </section>
  );
}
On the server
The component renders inside the same events context it hydrates inside, holding the server's events, so a component that calls useEvents() renders on the server as in the browser: a subscription made there is accepted and never called, and last answers nothing.
events.last(topic)
A page can name one stream, and every topic the stream sends keeps its last message, because the stream opens while assemblies are still loading. An assembly that mounts late reads what it missed with last, then subscribes.

When it runs in the browser

export const mount = "visible"
Declared by the view, beside its default export. load mounts at once and is the default; idle waits for the browser to be idle; visible waits until the envelope scrolls into view; none never mounts, and the assembly ships no JavaScript at all. A value that is none of the four reads as none, so a typo cannot start code running on a page whose author was saying when it should run.
export const shadow = true
Renders the assembly in its own shadow root: no page style reaches in, none of its own leaks out. The box from the shadow example, where every framework counts in a root of its own. 
import { createSignal } from "solid-js";

export const shadow = true;

export default function SolidBox() {
  const [count, setCount] = createSignal(0);
  return (
    <button type="button" class="bump" id="solid-bump" onClick={() => setCount(count() + 1)}>
      solid {count()}
    </button>
  );
}

Styles

cart.css
A stylesheet beside the view is compiled with a scope derived from the assembly's name, so two assemblies written apart cannot collide; the view in its own shadow root links a second sheet, built for that root. Every file it names beside it, an image or a font, is built with it; one it cannot carry is a build problem, not a broken link found later. The box above has one rule beside it. 
.bump {
  color: rgb(0, 128, 0);
}

On a page

<assembly name="cart"></assembly>
In any page template under src/pages. A local placement needs no policy at all.
home.page.ts
Policy, when a placement needs any, lives in the page's own file: a deadline in milliseconds, markup to show when the assembly does not answer, whether its failure fails the page, or a deferral the browser fills after load. 
import { definePage } from "@assemblejs/core";

export default definePage({
  place: { cart: { deadline: 500, fallback: "<p>Cart unavailable</p>" } },
});

Run it

npm run dev
Builds, starts, and rebuilds on every change.
npx assemblejs check
Every problem found without building: a placement naming an assembly that does not exist, policy nothing reads, the renderer not installed, a view named cart.tsx, which does not say its framework.
npx assemblejs build
Writes dist/server.js and the browser files. Production is node dist/server.js with no bundler.
